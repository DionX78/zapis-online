## 1. Что умеет система (для продаж и документации)

### 1.1. Для клиента клиники (Пациента)

- ✅ **Запись онлайн в MAX.** Mini App с календарём, без установки приложений. Видны только реальные слоты (прошедшее скрыто с буфером 30 мин).
- ✅ **Выбор услуги, даты, времени, специалиста.** Услуги сгруппированы по категориям (секции сворачиваются). Если на одно время есть несколько специалистов — клиент видит всех и может выбрать, не возвращаясь назад.
- ✅ **Учёт длительности.** Услуга на 90 мин занимает несколько подряд идущих слотов. Клиенту показываются только те слоты, где хватает времени подряд. Групповая бронь атомарна.
- ✅ **Буфер после приёма.** Учитывается при подборе подряд слотов.
- ✅ **Показ адреса.** Если приём в разных филиалах — адрес под именем специалиста, на экране выбора времени — секции по филиалам с пастельными цветами.
- ✅ **Любимый специалист.** Звёздочка ☆→★, приоритет в списке. Сохраняется в профиле.
- ✅ **Автозаполнение.** ФИО, телефон, пол, ДР при повторной записи. Галочка 152-ФЗ — только один раз.
- ✅ **Защита от дублей.** Нельзя записаться на слот дважды. Нельзя иметь 2 активные записи на одно время (даже к разным специалистам и на разные услуги). Лимит активных записей в день (по умолчанию 2, настраивается). Лимит 10 активных предстоящих записей.
- ✅ **Подтверждение + `.ics` в календарь.** Работает во всех точках: после `auto`, после подтверждения админом, после «✅ Приду» в client-режиме, после «✅ Подтверждаю» в напоминании.
- ✅ **Маршрут.** Ссылка на Яндекс.Карты и/или 2ГИС (настройка в клинике).
- ✅ **Три режима подтверждения:** `manual` / `auto` / `client` (с переспросом при отмене).
- ✅ **Напоминания 24 ч / 2 ч.** Тихие часы 22:00–9:00 в TZ клиники, «последний шанс» за час.
- ✅ **Согласие 152-ФЗ.** Галочка при первой записи, фиксируется время.
- ✅ **Мои записи.** Предстоящие / история, кнопки «↩ Повторить» по уникальным услугам (дедуп).
- ✅ **Заказать звонок.**
- ✅ **Отписка от рекламы.** Кнопка в каждой рассылке.
- ✅ **Блокировка клиентов.** Заблокированный не может записаться, видит свои записи.
- ✅ **Лист ожидания.** Клиент оставляет заявку («хочу на маникюр на этой неделе»), и получает уведомление, когда освобождается подходящий слот. Одна кнопка «✅ Записаться» в уведомлении создаёт запись сразу. Доступно из Mini App (кнопка «🔔 Сообщите, если освободится») и из бота (пункт меню «🔔 Лист ожидания»).

### 2.92. E4.6. Мультибот: свой бот у каждой организации

**Требование:** у каждой организации — свой бот. Сейчас MAX-бот один (`config.MAX_BOT_TOKEN`, один `WEBHOOK_PATH`, секрет в `X-Max-Bot-Api-Secret`), но `bots` уже устроена правильно — под мультибот.

- ⬜ **Почему это нельзя отложить.** Прямо сейчас MAX-вебхук на боевом сервере зарегистрирован с `WEBHOOK_SECRET`. Если VK-адаптер начнёт пользоваться `config.WEBHOOK_SECRET` — любые два бота будут иметь один секрет. Поэтому в E4.1 секрет **обязан** быть из `bots`. Обратное (VK → общий секрет) — это переделка позже.
- ⬜ **E4.6a. Схема (сделано частично).** `bots.group_id` и `bots.confirmation_code` добавлены, `upsert_bot` их принимает, миграция идемпотентна через `_ensure_column`. Осталось: `bots.unique(platform, group_id)` и бэкфилл единственного MAX-бота из `config` в `bots` при старте (slug `default-max`), чтобы код читал бота из БД, а не из env.
- ⬜ **E4.6b. Маршрутизация входящих по боту.** Сейчас `@router.post(config.WEBHOOK_PATH)` — один путь. Станет: `/max_booking/api/webhooks/{slug}` (+ старый путь как алиас для `default-max`, чтобы не ломать работающего бота). Путь MAX — `/max_booking/api/webhooks/default-max`, VK — `/max_booking/api/webhooks/vk-pboroda42`. Секрет ищется по slug, а не в `config`.
- ⬜ **E4.6c. `MAX_BOT_TOKEN` → `bot_id` по цепочке.** `core/auth.py` валидирует WebAppData HMAC'ом от токена *бота организации* — при мультиботе это токен той организации, чей Mini App открыт. Без этого Mini App второй организации не пройдёт авторизацию. `core/auth.py:32,54` — точки правки.
- ⬜ **E4.6d. Отправка по организации.** `core/max_client.py` и `core/channels/max.py` берут токен из `get_bot_for_org(org_id, 'max')` с фоллбэком на `config.MAX_BOT_TOKEN`. ~15 точек в `max_client.py`, но все через один хелпер `_auth_headers(org_id)` — правка механическая.
- ⬜ **E4.6e. UI «📡 Каналы»** — общий для MAX и VK: одна форма, `platform` выбирается. Сюда же переезжает кнопка «Проверить» и «Зарегистрировать вебхук».
- ⚠️ **Риск MAX:** у платформы MAX регистрация вебхука (`/subscriptions`) привязана к токену бота, так что каждый бот регистрируется своим токеном на свой URL. Проверить на втором тестовом боте до продажи.

**Итог:** мультибот — не «волна 3», а часть E4, но идёт после того, как VK заработает на одном боте. Порядок: E4.0 → E4.1 (секрет из `bots`) → E4.6a/b → E4.2 (UI сразу мультиботовый) → E4.3 → E4.6c/d → E4.4 Mini App.

Когда освобождается подходящий слот — клиент получает уведомление с кнопками «✅ Записаться» / «❌ Не нужно». Одна кнопка — и бронь создана.

Админ ставит клиента в лист вручную.** Админка → ⏳ Лист ожидания → «➕ Добавить в лист» → поиск клиента по ФИО/телефону (или ввод нового телефона) → услуга (опционально) и/или специалист (опционально) → период → время суток → заметка. - Первые `slot_backfill_delay_minutes` (по умолчанию 30 мин) — слот висит в обычном потоке (клиенты в Mini App его видят и могут записаться).
- Через 30 мин — воркер отправляет уведомление всем подходящим заявкам из листа (rate-limit 1/час на клиента, до 5 уведомлений на заявку).
- Ждёт `slot_backfill_waitlist_wait_minutes` (по умолчанию 30 мин). Если кто-то нажал «✅ Записаться» — бронь создаётся сразу, остальным offers → `taken`.
- Если никто не откликнулся — запускает backfill (см. сценарий 35).

**35. Backfill (горячие окна).** Воркер ищет клиентов, у которых уже есть активная запись на ту же услугу, но позже освободившегося слота (минимум на `slot_backfill_min_gap_hours` = 24 ч). Топ-N (по умолчанию 5) — самые близкие по времени. Им уходит предложение: «🔥 Освободилось более раннее время. Ваша текущая запись — <дата>. Перенести?». Кнопки «✅ Перенести» / «❌ Оставить как есть». При переносе — старая бронь освобождается, новая создаётся атомарно. Cooldown 24 ч на клиента, чтобы не спамить.

**36. Клиент записался сам, не через уведомление.** Клиент A стоял в листе ожидания, но записался на подходящий слот самостоятельно (через Mini App или админ создал ему запись). Заявка в листе автоматически закрывается (`fulfilled`) — чтобы не присылать ему уведомления, когда клиент уже записан.

**37. Заявка истекла.** Заявка в листе на период, который закончился, автоматически помечается `expired` (воркер раз в сутки). Клиенту ничего не приходит, в админке — в фильтре «⏳ Истекли».

## 1.7. Как работает лист ожидания и горячие окна (для документации)

### 1.7.1. Для клиента

**Зачем.** Клиент хочет записаться, но на подходящие даты нет слотов. Без листа — ему придётся заходить и проверять. С листом — система сама напишет, когда что-то освободится.

**Как встать.** Из Mini App: экран выбора времени → кнопка «🔔 Сообщите, если освободится». Или из бота: главное меню → «🔔 Лист ожидания» → «➕ Добавить заявку».

**Что указать.**
- Услуга (обязательна, если не указан специалист).
- Период (с какого по какое число ищем).
- Удобное время (утро / день / вечер / любое) — опционально.

**Что происходит дальше.**
- Заявка не занимает слот и не гарантирует запись. Ни к чему не обязывает.
- Когда освобождается подходящий слот — клиент получает в MAX уведомление с кнопками «✅ Записаться» / «❌ Не нужно».
- «✅ Записаться» — бронь создаётся сразу, стандартный поток (подтверждение / `.ics` / напоминания).
- Если клиент не успел — слот могли занять. Придёт «❌ время занято».
- Если клиент сам записался на подходящий слот — заявка в листе автоматически закрывается, уведомления по ней больше не приходят.
- Клиент может удалить заявку в любой момент.

**Ограничения.**
- Не чаще 1 уведомления в час (чтобы не спамить).
- Не больше 5 уведомлений на одну заявку (потом заявка замолкает, но остаётся активной — можно удалить вручную).
- Заявка истекает автоматически по окончании периода.

### 1.7.2. Для администратора

**Раздел «⏳ Лист ожидания»** (гамбургер-меню админки).

**Что видно.**
- Список заявок с фильтром по статусу (активные / все / выполненные / отменённые / истёкшие).
- Для каждой: услуга, специалист (если указан), период, время суток, клиент (ФИО + телефон), заметка, сколько раз уведомляли.
- Бейдж «нет MAX» для клиентов с `phone:` — им уведомления не доставляются, только админ может связаться по телефону.

**Что можно делать.**
- ➕ Добавить заявку вручную: поиск клиента по ФИО/телефону, либо ввод нового клиента (телефон + ФИО).
- ✏️ Редактировать: услуга, специалист, период, время суток, заметка.
- 🔔 Уведомить вручную: найти ближайший подходящий свободный слот и отправить клиенту уведомление (полезно, когда слот освободился давно, а клиент добавился только что).
- ✅ Выполнено: пометить заявку выполненной вручную (например, если запись оформлена другим способом).
- 🗑 Удалить: отменить заявку.

**Валидация:** при создании и редактировании нужно указать **хотя бы одно** из двух — услугу или специалиста.

**Сценарии использования.**
- Клиент звонит: «хочу к Ивановой на маникюр, когда что-то освободится». Админ: «только специалист Иванова + маникюр», период — неделя.
- Клиент звонит: «хочу на маникюр, любой мастер». Админ: «услуга маникюр, любой специалист».
- Клиент звонит: «хочу к Ивановой, услуга любая». Админ: «только специалист Иванова, без услуги».

### 1.7.3. Горячие окна (backfill)

**Зачем.** Когда слот освобождается, в листе часто никого нет. Тогда логично предложить перенос клиенту, который записан на эту же услугу, но на более позднее время. Специалист заполнит освободившееся окно плотнее, а освободившийся «поздний» слот ещё успеет кто-то занять по обычному потоку.

**Логика.**
1. Слот освободился (отмена / таймаут / перенос).
2. Через `slot_backfill_delay_minutes` (по умолчанию 30 мин) — уведомление листа ожидания.
3. Ждём реакции `slot_backfill_waitlist_wait_minutes` (по умолчанию 30 мин).
4. Если лист не откликнулся или все отклонили — ищем кандидатов:
   - клиент с активной записью на ту же услугу;
   - его запись как минимум на `slot_backfill_min_gap_hours` (по умолчанию 24 ч) позже освободившегося слота;
   - cooldown `slot_backfill_cooldown_hours` (по умолчанию 24 ч) между предложениями одному клиенту.
5. Отправляем предложения топ-`slot_backfill_max_candidates` (по умолчанию 5) клиентам с самой близкой подходящей записью.
6. Кто первый нажал «✅ Перенести» — тот переносится. Остальные offers → `taken`.
7. Освободившийся старый слот клиента идёт по обычному потоку (лист / backfill **не запускаем** — иначе бесконечная рекурсия).

**Универсальные слоты (без `service_id`).** Backfill для них **не работает** — не с чем сравнить услугу. Работает только уведомление листа (клиент с заявкой «услуга Y» ловит универсальный слот).

**Настройка.**
- «🔥 Горящие окна» в `⚙️ Настройки`.
- Включается одним чекбоксом.
- 5 полей с понятными подсказками.

**Чего НЕ делает.**
- Не переносит клиента без его согласия (только предложение).
- Не запускает backfill на универсальные слоты (нет услуги).
- Не запускает backfill дважды для одного слота (защита от каскада).

- Переотправка срабатывает в **обеих** точках проверки занятости: ранний `if slot["request_id"] is not None` и `result == "slot_taken"` после попытки брони.
- RAW-логирование callback'ов: `log.info("wl callback RAW: uid=%s payload=%r msg_id=%r", ...)` — для диагностики «кто что нажал».
- Логирование `cancel_waitlist_entry: wid=%s` в `storage/db.py` — если заявка отменяется, видно факт в логе.

### 2.61. Лист ожидания — авто-fulfill не по старым броням (10.11.2026)
- `_fulfill_waitlist_on_bookings_sync`: закрывает заявку (`fulfilled`) только если у клиента есть активная запись (`pending/confirmed`), созданная **после** заявки (`h.created_at > wl.created_at`). ### 2.72. TZ-унификация в листе ожидания и backfill (11.11.2026)
- **Проблема:** `slots.released_at` пишется триггером через `datetime('now')` (UTC в SQLite), а `slot_offers.sent_at` и `waitlist.created_at` — через `datetime.now()` в Python (local TZ сервера). Сравнения давали смещение на часовой пояс (+3 часа для МСК).
- **Последствия до фикса:** `slot_backfill_delay_minutes` фактически **не работал** — слоты обрабатывались сразу. TTL `slot_backfill_sent_ttl_hours` работал с погрешностью ±3 часа.
- **Фикс:**
  - `_process_released_slot` — `released_at` из триггера помечается как UTC (`tzinfo=timezone.utc`), сравнивается с `datetime.now(timezone.utc)`. Теперь `delay_minutes` реально ждёт.
  - `find_waitlist_matches_for_slot` — SQL: `datetime(o.sent_at) > datetime('now', 'localtime', ?)` (было `julianday(...) > julianday('now', ?)`). `sent_at` (Python local) и `now` (SQLite) теперь в одной TZ.
  - `_expire_daily` — per-org: `today_for_org(oid)` вместо `datetime.now()`. Для клиник не в МСК граница дня больше не сдвинута.
- **Что не трогалось** (работает корректно): `_flush_pending_offers`, `_fulfill_waitlist_on_bookings_sync`, `_sweep_stale_waitlists`, `now_for_org`, TZ организации, `slot_offers.sent_at`/`waitlist.created_at` (остаются local), триггеры БД (остаются UTC).
- **Изменение UX:** после фикса `slot_backfill_delay_minutes` реально работает (по дефолту 30). Раньше уведомление уходило сразу. Клиент в листе ждёт 30 мин + batch 15 = до 45 мин от освобождения слота. Это правильно по задумке, но повлияет на «ощущение скорости» у админа. При необходимости уменьшить — `Настройки → 🔥 Горящие окна → «Уведомлять лист ожидания через, минут»`.

### 3.3. Ресурсы (кабинеты, оборудование) — волна 3, по запросу
Отложено сознательно: первые продажи — в мелкие организации, которым
достаточно «один специалист — один кабинет». Делаем, когда появится
клиент с несколькими кабинетами / общим оборудованием.

**Согласованная модель (зафиксирована, чтобы не проектировать заново):**

- `resources` — справочник ресурсов.
  - `id, org_id, branch_id, name, type ('room' | 'equipment' | 'workplace'), active, notes`.
  - Примеры: «Кабинет 1», «Кресло у окна», «Аппарат лазерной эпиляции», «Солярий №2».
- `resource_services` — какие услуги **требуют** ресурс (многие-ко-многим).
  - Одна услуга может требовать несколько ресурсов (лазерная эпиляция → аппарат + кабинет).
  - Один ресурс может использоваться в нескольких услугах.
- `schedule_shifts.resource_id` (nullable) — опциональная привязка ресурса к смене специалиста.
  - Если указан — слоты из этой смены уже привязаны к конкретному экземпляру. Жёсткая привязка (салон: у мастера своё кресло).
  - Если не указан — слот «без ресурса», при бронировании подбирается **любой свободный** экземпляр. Гибкая привязка (клиника: общий аппарат УЗИ).
- `resource_bookings` (или поле в `slots`) — занятость ресурса на конкретном слоте/время.
- Валидация в `create_booking` / `admin_create_slot`: для каждого требуемого ресурса проверяем, что свободен хотя бы один экземпляр на всё время слота (с учётом длительности и буфера). Если нет — 400.
- **UI:**
  - «Справочники → 🚪 Ресурсы» — CRUD.
  - Карточка услуги — «Требуемые ресурсы» (мультиselect).
  - График специалиста (📅) — выпадающий список ресурса в каждой смене (опционально).
  - «Расписание» — режим отображения «по ресурсам» (занятость кабинетов), как в YCLIENTS.
- **MVP-упрощения:** не делаем «экземпляры» ресурсов (просто N отдельных записей), не делаем расходные материалы / склад.
- **Опора на конкурентов:** YCLIENTS (ресурс как дополнительное измерение поверх смены) и DIKIDI (ресурс как требование услуги, автоматическая проверка занятости).

- ⬜ `resources`, `resource_services`, `schedule_shifts.resource_id`, `resource_bookings`.
- ⬜ Проверка занятости ресурса при бронировании.
- ⬜ UI раздел «Ресурсы» + привязка в карточке услуги + выбор в смене.
- ⬜ `create_booking` — единая точка валидации (уже сложный, нужны тесты перед изменением).

**9.1. Лист ожидания + backfill (горящие окна)** — 2–3 недели

**9.1a. Лист ожидания.** Клиент хочет записаться, но на его даты нет слотов.
- Таблица `waitlist` (см. 3.6 ниже).
- API админа: `GET /admin/waitlist`, `POST`, `PUT`, `DELETE`, `POST /notify`, `POST /fulfill`.
- API клиента: `POST /mini/waitlist`, `GET /mini/waitlist`, `DELETE /mini/waitlist/{id}`.
- UI админки: раздел «⏳ Лист ожидания» в гамбургер-меню.
- UI Mini App: кнопка «🔔 Сообщите, если освободится» на экране выбора времени; блок в «Мои записи».
- Триггер на `release_slot`: уведомление подходящих из листа (rate-limit: 1/час на клиента, до 5 уведомлений на заявку).
- Воркер раз в сутки: `status='active'` с `date_to < today` → `expired`.

**9.1b. Backfill (горящие окна).** Клиент уже записан, но можно перетащить его на более раннее время, освободив более поздний слот.
- Новая таблица `slot_offers` (см. 3.6 ниже).
- Триггер: через `slot_backfill_delay_minutes` (дефолт 30) после освобождения слота — если лист ожидания не откликнулся (или был пуст), запускаем подбор.
- Подбор кандидатов: клиенты с активной записью на эту же услугу, чья запись минимум на `slot_backfill_min_gap_hours` (дефолт 24) **позже** освободившегося слота. Из нескольких активных записей клиента берём **одну** — самую близкую по времени к освободившемуся слоту среди подходящих. Сортируем клиентов по этой ближайшей записи, берём топ-`slot_backfill_max_candidates` (дефолт 5).
- Cooldown: не чаще одного такого предложения в `slot_backfill_cooldown_hours` (дефолт 24) на клиента.
- Сообщение: «🔥 Освободилось время: … Перенести?» + кнопки.
- При согласии: транзакция — проверка «слот свободен / запись клиента активна» → `move_booking` → уведомления → все остальные `slot_offers` по слоту в `taken`.
- При отказе: `slot_offers.status='declined'`, cooldown на клиента.
- **Без рекурсии:** освободившийся слот клиента после переноса идёт по обычному потоку (лист ожидания / общий), новый backfill по нему не запускаем.
- **Уровень 1:** если у клиента несколько активных записей на услугу — обрабатываем только одну (самую близкую к освободившемуся слоту).
